1. 9월 30일: CLI의 불필요한 영상·이미지 작업 줄이기

초기에는 저FPS로 영상을 샘플링하고 ROI·화면 변화를 분석한 뒤 대표 프레임을 PDF로 만드는 구조였다. 이 시점부터 다음 최적화가 실제 커밋에 남아 있다.

2. 10월 5~8일: 검출 정확성과 GUI 사용 흐름 정리

지정사 강의에서 슬라이드 누락과 과검출을 다루며 전역 차이뿐 아니라 국소 타일 변화, 기준 프레임·인접 프레임, 시간적 확인, 안정적인 대표 프레임을 검토했다. 같은 슬라이드가 다시 등장하는 경우를 무조건 지우지 않도록 전역 pHash 중복 제거도 기본 경로에서 배제했다.

이 단계의 핵심은 속도 배율이 아니라 무엇을 보존해야 하는지 정의하는 것이었다. 65개 테스트 통과나 추출 페이지 수 증가는 의미상 정확도 향상의 직접 증거가 아니다. 지정사 1~5장의 상태와 PDF 페이지 수 일치는 파이프라인 일관성 검증이며, 모든 교과목의 정답을 맞혔다는 뜻도 아니다.

CLI에서 필요한 코어를 가져와 독립 데스크톱 GUI로 확장했다. 저해상도 분석·미리보기와 최종 원본 출력 분리는 이후에도 유지했다.

3. 10월 9일, v0.4.4~0.4.5: 계측 후 캐시 병목 제거

먼저 준비·ROI·검출·JPEG 인코딩·캐시 쓰기·FFmpeg 대기를 분리해 기록했다. 프로파일의 sampling에는 JPEG/캐시 시간이 포함되므로 겹치는 항목을 더하지 않는다. decode_wait도 순수 디코더 CPU 시간이 아니다.

캐시 쓰기에서는 임시 JPEG마다 수행하던 디스크 동기화와 반복적인 저장소 조사·메타데이터 갱신을 줄였다.

  • 임시 JPEG의 독점 생성·원자적 rename은 유지하고 이미지마다 fsync는 제거.
  • 사용량을 증분 계산하고 저장공간을 최대8MiB 단위로 예약.
  • manifest는 32이미지 또는2초마다 갱신하고 완료 시 정확히 기록.
  • 미완성 캐시를 재사용하지 않고 활성 세션의 소유권과 정리를 관리.
  • 최종 PDF·JSON 출력 트랜잭션의 내구성은 유지.

4. v0.4.6~0.4.8: GPU와 스레드를 실험하고 실제로 빠른 CPU 경로 채택

사용자 Mac에서 31분720p 강의, 0.5FPS의 937샘플·17페이지 조건으로 비교한 기록이다. 아래 두 표는 서로 다른 벤치마크 실행이므로 CPU26.71과26.76의 차이를 추가 성능 개선으로 해석하지 않는다.

CPU 최적화는 샘플PTS·페이지PTS·구간과 JPEG 픽셀이 동일한 채 시간을29.8% 줄였다. 타이밍·색상·크기·인터레이스 메타데이터 검사는 유지했다. 제거한 것은 검증에 쓰이지 않던 픽셀 체크섬·통계 계산이다.

결론은 이 영상·기기의 구현에서는 CPU 자동 스레드가 명시적2/4 스레드와 GPU 경로보다 빨랐다는 것이다. VideoToolbox 지연 원인을 전송 하나로 확정할 분리 실험은 없으므로 하드웨어↔CPU 전달·필터 구조의 가능성으로만 기록한다. GPU 자체가 일반적으로 느리다는 결론도 아니다.

추가로 캐시 JPEG의 중복 사전 읽기를 없애고, 샘플/페이지 조회를 인덱스로 바꾸며, 원본 프레임 추출에도 최적화된 CPU 옵션을 사용했다(4bc1329). 각각의 독립적인 전체 처리 시간 감소율은 없다.

5. 0.4.11~0.4.12: 백그라운드 준비와 재사용으로 클릭 후 대기 줄이기

영상 선택 직후 백그라운드에서 샘플을 준비하고 Analyze에서 같은 캐시를 재사용하도록 했다. 준비가 끝나기 전에 분석을 눌러도 중복 디코딩하지 않도록 관리했다. 총120초 제한은 긴 강의를 잘못 중단시키므로 실제 진척이 멈춘 시간을 감시하는 방식으로 바꿨다. 실패한 준비 재시도, 취소·정리, 최신 미리보기 우선 처리도 보완했다.

이 작업은 전체 계산량 감소와 클릭 후 대기 감소를 구분해야 한다. 영상 선택과 동시에 분석을 누르면 숨겨둘 준비 시간이 거의 없다. 사용자가 0.5 초기 배포 후 “기대만큼 빠르지 않다”고 느낀 맥락도 이 차이와 연결된다.

M4의117분 영상에서 준비 완료 후 Analyze는 클릭~결과40.61초였지만 준비252.55초가 클릭 전에 수행됐다. 조기 Analyze는387.49초였다. 두 실행의 서버 부하도 달랐으므로 이 비율을 알고리즘의 속도 향상으로 쓰지 않는다.

6. 0.5 초기 M1~M5: FPS에서 키프레임·원본 PTS 중심으로 전환

출력 FPS를 낮춰도 FFmpeg가 중간 프레임까지 디코딩하면 영상처리 비용이 남는다. 따라서 디코더에서 비키프레임을 건너뛰고 실제 키프레임 PTS를 유지하는 구조로 전환했다. 고정FPS 격자를 전제로 한 모델·편집·JSON도 관측 순서와 원본 PTS 기반으로 바꿨다. FPS 경로는 제품에서 격리한 외부 비교 기준으로만 남겼다.

Linux Oracle A1 4 CPU, FFmpeg6.1.1, 동일 300초 구간 각 방식3회, 준비+캐시 분석 중앙값:

강의 0.5FPS 키프레임 all 시간 감소
시스템프로그램 15.154초 10.239초 32.4%
멀티코어 13.945초 12.911초 7.4%
AI윤리 14.414초 13.005초 9.8%

FFmpeg null 출력 대조에서는 CPU 시간이 SP78.6%, 멀티코어64.2%, 윤리65.1% 감소했다. 이 대조는 RGB·JPEG·캐시·검출·PDF를 제외한다. SP는각 3회 중앙값, 다른 두 강의는각1회다.

CPU가 크게 줄어도 앱 전체 향상이 제한된 이유는 키프레임이 약1초마다 있어 0.5FPS보다 이미지가 약2배 생겼기 때문이다. JPEG·캐시와 비교 비용이 증가했다. 예컨대34.9분SP 전체 1회에서는 준비94.35→58.30초지만 분석6.03→11.29초로 늘어, 합계100.38→69.59초였다.

이 시점의 인식 전환은 디코딩만 줄여서는 부족하며, 이후의 RGB·JPEG·캐시·검출 작업량도 줄여야 한다는 것이었다.

7. E1E3 및 M6M7: 절반을 쓰되 디코딩 이전에 선택하기

경쟁작의 패킷·GOP 정책을 조사한 뒤, 키프레임 간격이 짧으면 절반만 쓰는 아이디어를 검증했다.

  1. FFmpeg가 이미 디코딩한 프레임 중 절반을 버리는 실험에서는 디코더 CPU가 거의 줄지 않았다. SP2.874→2.870초, 멀티코어3.393→3.375초, 윤리3.568→3.557초였다.
  2. C++/libavformat/libavcodec에서 H.264 IDR 패킷을 디코더에 넣기 전에 골랐다. 제한된300초 클립에서 all→half CPU가 대략절반, 선택한PTS/YUV해시는 동일했다. JPEG·GUI는 이 실험에 포함되지 않았다.
  3. RGB·JPEG·캐시·실제 분석을 연결한 E3 프로토타입에서는 총시간25.8~50.9% 감소했다. 1회씩이고 제품 표시변환과 차이가 있어 최종제품 수치로 쓰지 않는다.
  4. M6에서 제품의 표시변환을 전용 디코더와 일치시켜 all 경로의 PTS/RGB/JPEG/전환을 대조했다. 이후 M7에서 디코딩 전half를 연결했다.

마지막에 채택한 정책은 패킷 검사상 GOP가 엄격히2초 미만이면 half, 그 밖은 all이다. 지원하지 않는 native 입력은 CPU의 전체 키프레임 경로로 돌아간다. FPS/P·B프레임 보충은 넣지 않았다. 요청한 정책과 실제 적용 정책도 구분해 기록한다.

8. 검출 코어 재설계: 사람의 검토량도 최적화

half 비교 중 윤리2~5번이 같은 슬라이드의 상태이고6번이 다른 짧은 슬라이드임을 사용자가 지적했다. 추적 결과 필요한 화면은 half에도 관측됐지만 기존 안정성·미래 확인 조건이 전환 확정을 막았다. 디코더가 관측하지 않은 문제와 검출기가 관측한 것을 버린 문제를 분리해야 했다.

지속적 국소 필기·순간 포인터는 같은 페이지 안에서 묶고, 짧게 나타나도 큰 구조 변화면 보존하도록 공간 변화 기반 그룹을 만들었다. 대표 프레임은 단순 마지막 프레임이나 오래 지속된 프레임 대신 누적 필기의 지지와 가림을 평가했다. 한 번만 관측된 큰 전환도 유효 그룹으로 남겼다.

초기 검토300초 클립 기존 all/half 후보 사용자 검토를 거쳐 수용된 그룹 all/half
SP 30 / 24 3 / 3
멀티코어 28 / 21 4 / 4
AI윤리 9 / 4 6 / 6

이 수치는 해당클립의 결과이며 일반적인 중복제거율·정확도가 아니다. 페이지 수가 줄어도 정답을 잃었으면 실패다. 실제 추가SP검증에서는 경계 기준이 작은 의미상 전환을 합쳤고 이를 드러내고 수정했다. 별도의 Notes 슬라이드는 오직 half가 버린 홀수키프레임에만 나타나 끝내 자동 검출에서 누락됐다. 후자는 검출기로 복구할 수 없는 입력 한계다.

슬라이드 회귀 식별은 사용자가 보류했으므로 과거페이지로 돌아온 정상적인 재방문을 무조건 지우지 않았다. 어시스턴트가 중간에 all을 기본으로 강제한 해석은 합의와 달랐고 M8에서half 기본과 편집을 복원했다. 이는 최적화 정책 수정 이력으로 남기며 all이 최종 기본인 것처럼 정리하지 않는다.

9. M8: half의 비용 절감과 전체 편집 가능성 양립

분석에 쓰는 이미지와 편집 가능한 키프레임 목록을 분리했다. 전체 PTS 인덱스는 유지하되 초기 JPEG는 절반만 만든다. 건너뛴 프레임이 미리보기·추가·교체·출력에 필요할 때 정확한 원본 PTS로 복원한다. 실제 backend/policy와 관측을 JSONv7에 기록하고 캐시 재사용도 정책에 맞춰 관리한다.

이 방식은 처음부터 전체JPEG를 만들지 않는 비용 이점을 유지하면서 수동 복구 가능성을 남긴다. 다만 사용자가 열어보지 않은 누락페이지를 자동으로 알아내는 기능은 아니다.

10. M9: 가장 신뢰할 수 있는 최신 전체 강의 반복 성능

Oracle Linux ARM64 4 CPU, FFmpeg6.1.1, 전체 강의3개×방식 3개×각 3회 = 27회. 새 프로세스·새 응용 캐시, 순차 실행. OS페이지캐시는 비우지 않았다. 중앙값은 probe+준비+캐시 분석이며 Python시작/모듈 import·정리·GUI·PDF는 제외한다.

같은 실험 안에서 전용 디코더만 적용한 효과는17.920.4% 감소다. Native/all에서half로 줄인 추가 효과는47.448.0% 감소다. 이 두 감소율을 더하지 않고 실제 CPU/all→half의56.858.6%를 쓴다. 패킷 검사 약0.370.62초도 준비 시간에 포함돼 있다.

전체 편집 인덱스는2020/4121/3021개를 유지한다. half의 메모리가 무조건절반이라는 주장은 하지 않는다. 부모 Python 메모리는 주로6471MiB였고 자식 최대치는CPU/all 약8789MiB→ native 약58MiB였다. 서로 다른 시점의 최댓값을 더해 동시 전체 메모리라 부르지 않는다.

SP전체all44회/half39회, 멀티코어11/11, 윤리59/59였다. 이것은시간순 페이지 출현 수로, 고유 슬라이드 수나 정답 재현율이 아니다. SP Notes 홀수 키프레임 누락도 남는다. 세번반복의결과일치는재현성증거이며 모든영상의정확성보장은아니다.

11. M10~0.5.0b2: 측정한 구조를 실제 배포 가능한 제품으로 마무리

전용 디코더와 고정 소스FFmpeg8.1.2를MacARM64·Windowsx64에 동봉했다. 실제 OS에서 설치 후half·지연복원·편집·PDF/JSON·Qt교체실행을검증했고, 한글 경로와 Mac Bash 호환성을 수정했다. 대응 소스·라이선스·재링크 자료와 파일 해시를 묶어 공개했다. 최종 소스 테스트1012개 통과, 사용자가 Mac 작동을 확인한 뒤 공식 베타0.5.0b2를 게시했다.

FFmpeg6→8품질 확인은6개 클립의 관측 PTS·24개 그룹 구간 동일, 대표 PTS8개 변경은 이미지 비교로 점검했다. 새 배포본의전체 강의처리 시간은 실기기에서 반복 측정하지 않았다. 따라서 M9의2.4배를새 배포본의모든기기성능보장으로 전환하지 않는다.

PDF와초기~최신누적수치에대한정리

PDF는원본 해상도 출력·정확한 PTS·검증·파일 크기에 영향받는다. 초기 일괄 추출·qpdf·조회 최적화와 검출 후보 감소는 도움이 되지만 동일 페이지·동일 화질의 초기/최신 반복 대조가 없다. M4의970상태PDF저장1147초와나중의적은 페이지 저장을 비교해 저장 속도 향상이라 부르면 작업량이 달라 왜곡된다.

안전하게 설명할 성과는 아래 세 가지다.

  1. Mac에서 확인한 초기 개선: 캐시와 불필요한 픽셀 작업을 줄여 당시 회고 기준80.40→18.79초. 약4.28배, 원본 일부 재확인 제한을 함께 표기.
  2. 최신 서버 반복 실험: 기존 키프레임 CPU/all 대비 전용 디코더+half로56.858.6%시간 감소, 약2.322.42배. JPEG캐시는약 절반.
  3. 품질·사용성 개선: 필기·포인터 중복을 묶고 짧은 큰 전환을 보존하며, 초기 이미지를 줄인 상태에서도 전체 키프레임 편집을 유지. 입력 누락·회귀 식별의 남은 한계는 명시.

전체 과정을 관통하는 설계는 비싼 처리를 더 일찍 줄이고, 필요할 때만 원본을 복원하는 것 이었다. 파라미터만 낮추는 최적화가 아니라 디스크·픽셀 검증·디코딩·이미지수·사람의 검토량을 차례로 줄인 과정이다.
