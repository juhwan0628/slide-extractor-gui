# M4 — 실제 강의 검증 결과
상태: 전체/반복 측정·회귀·독립 리뷰 완료. 릴리즈/네이티브 검증 완료를 뜻하지 않습니다.

## 범위와 측정 조건
제품 코드는 M3 `41c1475`와 동일합니다. 계측 도구와 검증 테스트만 추가했습니다.
Linux Oracle A1/aarch64, 4 CPU, Python3.12.3, FFmpeg6.1.1, 모든 실영상1280×720 H.264.
서버의 다른 작업과 일부 병행 검증이 CPU를 사용했습니다. wall시간은 이 환경의 관측값이며 단독 실행 성능/네이티브 설치본 속도의 보장이 아닙니다.
새 응용 캐시를 매번 만들고 끝나면 소유권을 해제해 삭제했습니다. OS 파일 캐시는 비우지 않았습니다.

- 원본 전체: SP34.9분, 멀티코어117.3분, AI윤리49.9분, 키프레임/외부0.5/1FPS 각1회.
- 반복 비교: 영상 중간의 동일300초 구간을 재인코딩 없이 remux한 별도 소스로, 각방식3회 순서를 회전해 실행했습니다. clip 시간 원점은 원본 강의와 구분합니다.
- 키프레임 전체 PDF+상세JSON은 소스별1회 검증. FPS의 SP PDF는 초기 참고 기록이며 페이지 수/저장 방식이 달라 속도 비교로 쓰지 않습니다.
- 같은20개 대표 페이지의 PDF+상세JSON 저장은 소스별3회, 총9회 완료했습니다.
- 실제117분 소스의 조기/준비완료 Analyze 경로도 별도로 검증했습니다.
- FPS 기준선은 고정 커밋 `4a8d486db124e31b130d37055985fa1e631ae300`을 archive한 별도 소스·별도 Python 프로세스입니다. 앱 의존성과 fallback이 아닙니다.

## FFmpeg CPU 대조 실험
같은 전체 원본을 `-an -sn -dn -fps_mode passthrough -f null -`로 출력하며 `-skip_frame nokey` 유무만 바꿨습니다.
자식 FFmpeg의 user+system CPU시간입니다. demux와 null출력 비용도 포함하고, RGB 변환·JPEG·파일 기록·감지·PDF는 제외합니다. 제품의 pipe 소비자 `decode_wait`를 decoder CPU시간으로 해석하지 않습니다.

| 소스 | 전체 프레임 CPU초 | 키프레임 CPU초 | 감소 | 반복 |
|---|---:|---:|---:|---|
| SP |89.289|19.136|78.57%|각3회 중앙값|
| 멀티코어 |227.854|81.540|64.21%|각1회|
| AI윤리 |102.987|35.917|65.12%|각1회|

중단한 미완료 대조 실행은 집계하지 않았습니다. 다른 두 소스의 CPU 변동폭은 검증하지 않았습니다.

## 완료된 전체 출력과 사용자 경로
멀티코어 키프레임 전체:7044관측,970자동 페이지, 준비256.53초+준비된 캐시 분석63.98초.
PDF+상세JSON 전체 저장1147.23초, PDF349002217바이트. 내부 page/geometry/UUID/JSON참조/해시 검증 및 공개 트랜잭션 완료.
970은 실제 교안 슬라이드 수가 아니라 필기/커서를 포함한 변화 상태 수입니다.
부모 maxRSS2097236KiB(약2.00GiB), 가장 큰 자식1187888KiB입니다. 서로 다른 시점의 highwater marks를 더하지 않습니다.
쓰기·검증 구간에서1초 간격으로 관측한 프로세스 트리 PSS최대2095496KiB(관측 하한), RSS합2114076KiB였습니다.

조기 Analyze: 준비312.35초, 이후 분석75.14초, 클릭~결과387.49초.
준비 완료 후 Analyze: 준비252.55초는 클릭 전 작업이며, 클릭~결과40.61초.
서버 부하가 달랐으므로 두 값의 비율을 동일 조건 속도 향상으로 주장하지 않습니다.
두 경우 모두 실제 디코더 명령1회, 캐시 재사용, 정상 완료 및 background cleanup을 확인했습니다. 120초 경과로 작업이 종료되지 않았습니다.
이것은 실제 BackgroundSamples+분석 경로의 측정이며 Qt 이벤트/화면 그리기 전체를 포함한 네이티브 UI 측정은 아닙니다.

20페이지 저장 중앙값: SP31.912초, 멀티코어41.118초, AI윤리40.108초. 각3회 모두 동일 소스의 동일 대표PTS·페이지 수입니다.
프로세스 lifetime maxRSS는 shared worker에서 측정되어 소스별 독립 peak가 아닙니다.

## 정확성 범위
SP 키프레임220개 대표 썸네일과0.5FPS171개를 모두 육안 확인했습니다. 필기 누적·애니메이션·재방문을 관찰했고, 페이지 수를 고유 슬라이드 수로 세지 않았습니다.
멀티코어는 시작·중간·끝90개 대표 썸네일을 확인했습니다. 전체970개에 대한 ground-truth recall/precision을 주장하지 않습니다.
모든 실영상의 최종 필기 상태가 완전하다고 주장하지 않습니다. 마지막 관측 이후 생긴 변화는 키프레임 전용 경로에서 보장하지 못합니다.

AI윤리59개 대표 썸네일도 모두 확인했습니다. 내장 영상/커서 변화로 생긴 추가 페이지와 끝의 검은 화면1페이지는 수동 검토·삭제 대상입니다. 새 방식이 의미상 슬라이드만 자동으로 분류한다는 뜻은 아닙니다.

정답이 알려진22초 테스트: A→2초 B→A→C. 1초 GOP에서는 B와C검출,10초 GOP에서는 관측0/10/20초만 있어 B누락·C검출.
긴 GOP에서 FPS/비키프레임 보충을 하지 않았습니다. 키프레임은 슬라이드 전환 자체를 뜻하지 않습니다.

## 검증
- 신규 계측/GOP 집중9개 통과22.59초.
- 전체 제품 회귀792개 통과262.05초, 종료코드0.
- 전체36회 집계와 반복 관측/대표/감지 배열 동일성 검증 완료. 독립 리뷰는 남았습니다.
- 실제 Mac·Windows 새 설치본, 1080p/4K, 지원되는 모든 코덱의 qualification은 수행하지 않았습니다.

## 판단 기록
1. 부하 있는 호스트의 wall시간을 단독/native 성능으로 해석하지 않습니다. 비용: native 측정은 M5로 남습니다.
2. 처음에는 전체3회와 모든 방식 PDF를 계획했으나, 페이지 수가 다른 PDF의 비교가 작업량을 혼동하고 고부하 전체 반복이 단독 속도를 확정하지 못해 변경했습니다. 비용: 전체 소스3회 중앙값과 동일 작업량의 legacy PDF속도 주장은 하지 않습니다.
3. 현재 전체 소스 각1회+중간300초3회, 실제117분 조기/완료 Analyze를 검증합니다. 비용: 반복 clip 비용과 전체 강의 완료 안전성은 서로 다른 증거입니다.
4. CPU/null 반복은 SP3회, 나머지 각1회로 제한했습니다. 비용: 다른 두 입력의 CPU 변동폭은 미측정입니다.

## 배포 전 판단
디코딩 CPU 절감과 키프레임 전용 모델/저장 계약은 실영상에서 확인했습니다. 가장 큰 남은 비용은 많은 페이지의 원본 해상도·무손실 PDF 생성과 검증입니다.970페이지 사례의 저장19.12분·약2GiB 부모 peak는 이 고부하 서버에서의 측정입니다.20페이지 결과와 작업량이 달라 두 시간을 동일 작업량의 속도 비교로 사용하지 않습니다.
Mac·Windows 네이티브 출고 및0.5.0 버전 반영은 M5입니다. 현재 배포본을 갱신하지 않았습니다. 긴 GOP/마지막 관측 이후 필기 누락의 한계는 유지되며, 보장되지 않는 입력의 안내와 PDF 비용 최적화는 배포 준비에서 따로 판단해야 합니다.
숫자 원본의 공개 가능한 요약은 Keyframe-M4-measurements.json에 저장했습니다. 강의 영상·이미지·원본 경로는 공개 Git에 포함하지 않습니다.

## 최종 독립 리뷰 및 보류 항목
Critical/Important 지적 없음. 리뷰어의 별도 집중 검증은 9 passed (15.16s), 전체 회귀 기록은 792 passed (262.05s)입니다.

Minor 두 가지는 후속 계측 문서 개선으로 남깁니다. 첫째, 공개 JSON의 worker_commit은 최종 도구 버전이며 초기 SP 기록은 1ed7798 계측에서 시작했고 일부 초기 전체 기록은 소스 가드/디코더 횟수/저장 단계 카운터 추가 이전입니다. 모든 행이 동일 계측 버전에서 생성됐다는 의미가 아닙니다. 둘째, 반복 범위와 JPEG/캐시쓰기/탐지 세부 프로파일은 비공개 원자료에 남아 있으나 공개 요약에는 모두 포함되지 않았습니다. worker 전체 CPU는 선택적 export/contact-sheet 작업까지 포함할 수 있어 순수 준비 CPU로 해석하지 않습니다.

별도 RGB 파이프 대조 실험으로 비용을 분리했다는 근거는 확립하지 못했습니다. 관측된 파이프 대기는 고립된 디코더 CPU가 아닙니다. 전체 소스 반복 분산, 같은 작업량의 FPS PDF 성능, 모든 슬라이드·최종 필기 상태의 recall 및 Mac/Windows 설치본 성능도 이 M4 결과로 보장하지 않습니다. 기존 범위 결정과 해당 비용은 위 결과의 제한으로 유지합니다.
